универсальное тз на РАЗРАБОТКУ (не анализ чужого кода).
рядом всегда будет конкретное тз задачи — читай его внимательно: путь/имя выхода, сигнатура, ограничения библиотек, примеры, ожидаемое поведение.
это общее тз задаёт СТИЛЬ и КАЧЕСТВО кода. конкретное тз задаёт ЧТО делать и ЧЕМ пользоваться.
если в конкретном тз тип/ограничение не сказано — не выдумывай сверхпроверки и не усложняй.

────────────────────────────────────────
0) БИБЛИОТЕКИ И API (по умолчанию)
────────────────────────────────────────
- по умолчанию: ВСЕ стандартные пакеты Go и любые функции разрешены; ограничений нет
- ограничения появляются ТОЛЬКО если их явно написали в конкретном тз (Allowed functions / Forbidden / только z01 и т.п.)
- если список Allowed задан — используй строго его (+ builtin, если разрешены); не подтягивай fmt/strconv/os «для удобства»
- если Allowed не задан — пиши самым ясным и коротким способом на stdlib

────────────────────────────────────────
1) ЦЕЛЬ РЕЗУЛЬТАТА
────────────────────────────────────────
нужен лаконичный, быстрый, корректный код:
- один проход там, где хватает одного; без повторного сканирования «на всякий случай»
- без лишних аллокаций: не копируй строку/слайс, если достаточно индексов или печати на лету
- без мёртвого кода, недостижимых веток, дублирования одной и той же логики в N файлах
- без паники/runtime error там, где по тз ожидается спокойный отказ (0 / false / пустой вывод / return)

────────────────────────────────────────
2) СТРУКТУРА КОДА
────────────────────────────────────────
- пиши только то, что нужно задаче
- если несколько похожих вариантов (например QuadA..E) — один универсальный хелпер + тонкие обёртки; по возможности один файл, без копипасты
- мелкие чистые хелперы (isVowel, hasPrefix) — ок, если убирают шум из основного потока
- циклы: начинай с 0, если нет явной причины стартовать с 1 (1-based только когда это совпадает с условием «от 1 до n» или координатами из тз)
- предпочитай range по строке/слайсу, когда индекс не нужен; индекс — когда нужен
- ранний return на граничных случаях (нет args, x<=0, пустая строка) — до основной логики

────────────────────────────────────────
3) КОММЕНТАРИИ (обязательны, но короткие)
────────────────────────────────────────
описание функций (перед объявлением):
- у КАЖДОЙ функции, кроме main, — комментарий СРАЗУ НАД func
- main не описывай: это точка входа
- в комментарии обязательно:
  1) что делает
  2) аргументы: что значит каждый (тип/смысл)
  3) результат: что возвращает / печатает; граничный случай если есть (nil, 0, пусто…)
  4) короткий пример входа → выхода
- 3–6 строк достаточно; не копируй сигнатуру дословно
- между концом предыдущей функции и комментарием следующей — одна пустая строка

хороший тон над функцией:
  // MakeRange собирает целые числа в полуинтервале [min, max).
  // min, max — границы диапазона (max не входит).
  // Возвращает []int; если min >= max — nil.
  // Пример: MakeRange(5, 10) → [5 6 7 8 9]; MakeRange(10, 5) → nil.
  func MakeRange(min, max int) []int {

этапы внутри функции — не каждая строка:
- нумерованные шаги в main/ключевой функции: // 1. ..., // 2. ..., // 3. ...
- у неочевидной проверки — «зачем» (не «что делает if» дословно)
- не комментируй очевидное (i++ // увеличиваем i)
- язык комментариев: русский, в том же стиле что и конкретное тз (если тз на EN — можно EN)

воздух между блоками (обязательно):
- перед комментарием нового этапа — одна пустая строка (кроме самого первого блока сразу после `{`)
- не сливай этапы вплотную: код+коммент+код без пустых строк читать тяжело
- не ставь больше одной пустой строки подряд; внутри одного этапа пустые строки не нужны

хороший тон внутри:
  // Foo делает …
  func Foo(...) {
  	// 1. Нет аргументов — только '\n'
  	if ... {
  		return
  	}

  	// 2. Собираем гласные со всех args
  	...

  	// 3. Печатаем, подставляя гласные с конца
  	...
  }
────────────────────────────────────────
4) КОГДА И ЧТО ПРОВЕРЯТЬ
────────────────────────────────────────
включай проверку ТОЛЬКО если она следует из конкретного тз (явное условие или тип входа):

1) форма входа
   - число / строка / rune / bool / слайс / os.Args — как в задаче
   - пустая строка, nil/пустой слайс, нет аргументов
   - лишние / недостаточно аргументов
   - нечисловая строка там, где ждут число — только если задача это затрагивает

2) диапазоны (если в тз есть «положительные», «>0», «от a до b» и т.п.)
   - 0, отрицательные, слишком большие
   - переполнение int — только если реально по смыслу
   - индекс вне длины

3) строки / символы
   - пустая / один символ / длинная
   - unicode/rune — если задача про rune; если про byte и не сказано — не усложнять

4) деление / циклы / границы
   - /0, выход за пределы, off-by-one, вечный цикл

5) «плохой» ввод
   - заранее зафиксируй безопасный исход из тз (0 / false / молча / help)
   - не падай, если по условиям должен быть спокойный отказ

────────────────────────────────────────
5) УЗКИЕ МЕСТА (в ответе рядом с кодом)
────────────────────────────────────────
кратко перечисли только релевантные защите пункты:
- ситуация: ...
  пример: ...
  защита: ... (не падает / возвращает X / молчит / ...)

не раздувай список. если входа нет (например «напечатай 0..9») — блок можно опустить.

────────────────────────────────────────
6) ФОРМАТИРОВАНИЕ (обязательно в конце)
────────────────────────────────────────
когда скрипт(ы) готовы и записаны на диск — прогони форматирование Go:
  gofumpt -w <путь-к-файлу-или-пакету>
если gofumpt недоступен: gofmt -w <тот-же-путь>
цель: убрать «грязные» пробелы в пустых строках, лишние/кривые переносы, неверный отступ — чтобы файл соответствовал канону gofmt/gofumpt.
после правки руками (комменты, воздух между этапами) — снова gofumpt -w, не оставляй сырой вывод модели без прогона.

────────────────────────────────────────
7) ЧЕГО НЕ ДЕЛАТЬ
────────────────────────────────────────
- не смотри соседние скрипты как образец решения; опирайся на конкретное тз + это общее
- не усложняй архитектуру (интерфейсы, куча файлов, «паттерны») ради красоты
- не оставляй отладочный fmt/печать лишнего
- не пиши тесты/main-демо, если конкретное тз их не просит
- не дублируй одну логику в пяти почти одинаковых функциях — вынеси общее
- не считай задачу завершённой без gofumpt/gofmt -w по готовым .go
